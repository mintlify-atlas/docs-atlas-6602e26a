K64 reads its runtime configuration from the GRUB Multiboot kernel command line, parsed in `k64_config.c` at the very start of `k64_kernel_main()` before any subsystem is initialized. The parsed values are stored in the global `k64_config_t` struct declared in `k64_config.h` and referenced throughout the kernel for timer frequency, log verbosity, and boot behavior. There are exactly three recognized keys; unknown keys are ignored silently.

```c
// k64_config.h
typedef struct {
    uint32_t       pit_hz;
    k64_loglevel_t log_level;
    char           boot_mode[16];
} k64_config_t;

extern k64_config_t k64_config;
```

---

## Configuration Keys

| Key | Type | Default | Description | Valid Values |
|---|---|---|---|---|
| `pit_hz` | integer | `1000` | PIT interrupt frequency in Hz. Controls how often the PIT fires and how fine-grained the tick counter and scheduler slices are. | Any positive integer; typically `500` or `1000` |
| `log_level` | string | `debug` | Kernel log verbosity level. Maps to `k64_loglevel_t` in `k64_log.h`. | `debug`, `info`, `warn`, `error` |
| `boot_mode` | string | `live` | Controls post-boot behavior. `live` is the normal interactive shell mode. `installer` opens K64's text installer guide after the service plane starts. | `live`, `installer` |

### Log Level Enum

The `log_level` key maps directly to the `k64_loglevel_t` enum:

```c
// k64_log.h
typedef enum {
    K64_LOGLEVEL_DEBUG = 0,
    K64_LOGLEVEL_INFO  = 1,
    K64_LOGLEVEL_WARN  = 2,
    K64_LOGLEVEL_ERROR = 3,
} k64_loglevel_t;
```

Messages below the configured level are suppressed. `debug` is the most verbose; `error` is the quietest.

## Example GRUB Menu Entries

### Standard development entry (verbose, normal boot)

```text
multiboot /boot/k64-kernel-v0.3.x.elf pit_hz=1000 log_level=debug boot_mode=live
```

### Quieter output, normal boot

```text
multiboot /boot/k64-kernel-v0.3.x.elf pit_hz=500 log_level=info
```

### Installer mode

```text
multiboot /boot/k64-kernel-v0.3.x.elf boot_mode=installer
```

Keys that are omitted fall back to their defaults: `pit_hz=1000`, `log_level=debug`, `boot_mode=live`.

## Where GRUB Configs Live

K64 uses two separate GRUB configuration files at different points in the boot path:

<Steps>
  <Step title="ISO bootstrap config">
    Generated into `build/grub-bootstrap.cfg` and installed as `iso/boot/grub/grub.cfg` inside the ISO image. This is what GRUB reads first when booting from the ISO. Its job is to load the `k64xfs` GRUB module, locate the rootfs, and offer the **Try K64 live** and **Install K64** menu entries.

    - The live entry passes `boot_mode=live`.
    - The installer entry passes `boot_mode=installer`.
  </Step>
  <Step title="Rootfs GRUB config">
    Generated into `build/grub-root.cfg` and copied into the staged rootfs as `/boot/grub/grub.cfg`. This is the "real" config stored inside the K64XFS volume. When a writable disk is attached, GRUB reads this file from the disk's K64XFS partition rather than the ISO copy.

    The default menu entry in this file is:

    ```text
    multiboot /boot/k64-kernel-v<version>.elf pit_hz=1000 log_level=debug
    ```
  </Step>
</Steps>

Both files can be edited directly in the GRUB menu at boot time by highlighting the entry and pressing **`e`**, which lets you modify the `multiboot` line before pressing **`F10`** or **`Ctrl-X`** to boot.

## Development vs. Production Log Levels

<Tip>
Use `log_level=debug` when running in QEMU or during development. It prints full boot diagnostics, driver registration messages, service start/stop events, and filesystem mount details to both the VGA terminal and the COM1 serial line. Switch to `log_level=info` or `log_level=warn` for quieter output when the system is behaving correctly and you do not want the boot sequence dominated by diagnostic lines.
</Tip>

## Kernel Image Versioning

The kernel image filename embedded in the GRUB `multiboot` line includes the full version string: `k64-kernel-v<major>.<minor>.<patch>.elf`. The version is assembled from three sources:

| Source | Purpose |
|---|---|
| `k64_version.h` — `K64_VERSION_MAJOR` | Manually controlled major version |
| `k64_version.h` — `K64_VERSION_MINOR` | Manually controlled minor version |
| `build/k64_autoversion.h` — patch | Auto-generated by `tools/gen_k64_version.py` as `git rev-list --count HEAD` minus `K64_VERSION_PATCH_BASE_COUNT`, plus 1 if the working tree is dirty |

Only changes to tracked kernel and runtime paths (top-level `*.c`, `*.h`, `*.s`, `*.S`, `linker.ld`, `k64m/`, `k64s/`, `ex/`, `grub/`, `rootfs/`) count toward the patch number. Repository housekeeping changes (`.github`, tests, tooling) do not bump the kernel version. A deliberate series jump such as `0.4.0` is done by updating `K64_VERSION_MAJOR` / `K64_VERSION_MINOR` and resetting `K64_VERSION_PATCH_BASE_COUNT` to the current commit count.

The generated filename propagates through the staged `/boot` directory in the rootfs, both GRUB configs, `sysfetch`, `uname`, and the hot-reload kernel-discovery path.
